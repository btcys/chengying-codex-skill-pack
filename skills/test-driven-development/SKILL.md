# 测试驱动开发

## 核心规则

```text
没有先看到测试因目标行为而失败，就不要写对应生产实现。
```

如果实现已经先写，测试无法证明自己能发现缺陷。只撤回或隔离本轮代理能够明确识别的实现改动；归属不明或可能属于用户的未提交改动必须停止并确认，不得删除或暂存用户成果。随后从失败测试重新开始；不要边看实现边反推只会通过的测试。

## 适用与例外

严格使用：Bug、业务规则、状态机、API、数据变换、权限、计费、公共接口和可回归的工程行为。

不强制失败测试先行：纯CSS、布局、文案、静态资源、fixture、生成文件和简单配置。它们仍需真实页面、交互、Golden、lint、typecheck或构建验证。

Spike或一次性探索代码只有在明确标为丢弃时可跳过；要保留为生产代码必须重新按TDD实现。

## RED-GREEN-REFACTOR

### RED：写一个最小失败测试

- 一次只描述一个可观察行为；
- 使用真实接口，除非外部边界确实需要mock；
- 名称说明条件和结果；
- Bug修复先写能重现Bug的测试。

### 验证RED

运行精确测试命令并确认：

- 测试失败而不是测试代码报错；
- 失败原因正是缺失行为；
- 如果测试直接通过，说明覆盖了旧行为或断言无效，先修测试。

### GREEN：最小完整实现

只写让当前行为正确通过的代码，不顺手加入未来选项、通用框架或无关重构。

### 验证GREEN

重新运行同一测试，确认通过；再运行受影响的邻近测试。不得只看进程退出或截断输出。

### REFACTOR

在保持测试绿色的前提下改善命名、重复和边界。每次小改后重新运行相关测试。

## 好测试

详细判断见 [writing-good-tests.md](references/writing-good-tests.md)。优先验证行为和合同；避免只验证mock调用次数、私有实现、常量复制或测试专用生产分支。

## 卡住时

- 不知道怎么测试：先写希望存在的调用接口，暴露设计问题；
- 测试准备过大：接口可能耦合过重，先缩小依赖；
- 必须mock所有对象：考虑依赖注入和边界抽离，但只做本次需要的改动；
- 测试不稳定：使用系统化调试和基于条件的等待，不增加任意sleep。
