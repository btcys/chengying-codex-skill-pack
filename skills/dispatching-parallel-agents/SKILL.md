# 并行派发独立子智能体

核心原则：每个独立问题域一个代理，同时运行，最后由主任务统一整合。

## 使用条件

- 多个失败来自不同模块或不同根因；
- 每个任务无需依赖其他任务的未完成结果；
- 不修改相同文件、核心接口、Schema或共享生成物；
- 不争用同一数据库、服务、端口或外部资源；
- 主任务可以分别验证并在最后运行整合测试。

任何条件不满足就顺序执行。尚未找到根因的探索性Bug不要先并行修复；先系统化调试并判断是否真独立。

## 流程

1. 按根因和职责把问题分组，不按文件数量机械拆分。
2. 为每个代理写自包含简报：目标、范围、相关错误、输入路径、禁止修改范围、验证命令和返回格式。
3. 明确告诉每个代理不得继续派发子智能体。
4. 在同一轮同时派发；遵守运行时并发上限和项目AGENTS指令。
5. 等待结果时主任务只做不冲突的统筹、调查或集成准备。
6. 返回后阅读实际diff和报告，检查是否有重叠或矛盾。
7. 按`verification-before-completion`核对各批次定向证据，补跑缺失或失效部分，再完成必要的整合验证，不重复子智能体已提供的有效测试。

## 好的简报

```markdown
目标：修复 `src/upload/upload-state.test.ts` 中列出的3个失败。

范围：上传状态机和对应测试；不要修改权限、素材列表或公共错误组件。

已知现象：<测试名、错误信息、复现条件>

要求：先找根因；不要仅增加timeout；适用时先写失败测试；不新增依赖；不commit；不得派发子智能体。

验证：`<准确命令>`

返回：根因、修改文件、测试命令与结果、剩余风险。
```

## 常见错误

- “修好所有测试”范围过大；
- 只给一句“修race condition”而没有错误和文件；
- 多个代理改同一共享模块；
- 并行代理各自运行完整测试套件；
- 代理返回摘要后不检查实际diff；
- 把并行当作默认，忽略依赖和集成成本。
