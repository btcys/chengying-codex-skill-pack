# 前端六点实施规则

仅在任务涉及页面、组件、交互、前端状态、数据流、视觉或动效时按需读取。本文件是开发和评审检查表，不是独立UI线程、Preview工程或新的审批阶段。

## 读取边界

- 简单样式或文案改动只检查第5点；状态问题重点检查第3点；共享组件问题重点检查第4、6点。
- 新页面、重大布局或跨页面改动才综合检查六点；不因文件出现CSS、Tailwind或动画库而全量读取。
- 只把相关条目和当前Spec、Plan、Task、Golden或Evidence交给子智能体，不传完整PRD、历史文档或其他批次报告。

## 六点检查

### 1. 先确认用户任务和业务对象

明确用户要完成的任务、页面管理的核心对象、字段所有者和可观察完成结果，再决定使用列表、详情、选择器、表单、弹窗或工作区。项目原有模式导致识别或操作错误时，不继续复制。

### 2. 删除无效信息和伪操作

每段可见文字、图标和动作至少服务于识别对象、区分对象、表达状态、说明限制、执行动作或反馈结果；否则删除。删除UUID、内部枚举、重复说明、重复确认和无真实结果的控件。代码注释只解释非显然的原因、边界或风险，不复述代码正在做什么。

### 3. 保证数据、状态和作用域真实

明确权威数据源、完整集合与当前可见集合、操作范围和最小忙碌范围。区分`loading`、`refreshing`、`empty`、`error`、`queued`、`processing`和`ready`；单项请求不阻塞无关区域。异步失败保留当前对象、位置、输入和恢复动作，成功后再关闭弹窗或更新提交边界。

### 4. 让界面结构和代码各自归位

列表负责识别和比较，详情负责完整内容，编辑器负责修改；页面负责组合，组件负责自身视觉和状态，Hook负责状态与副作用，请求和持久化放在业务或数据访问层。先搜索已有组件、Token、父布局和默认行为，再决定新增或修改；共享问题修共享源头，不在页面使用位置反复覆盖样式。

### 5. 让视觉与动效真正落地

视觉按“信息层级→空间与对齐→排版→表面→控件状态→动效”处理，优先复用项目Token、组件、密度和相邻页面模式。使用真实内容和相关状态验证；动效说明用途、触发、起止、可中断和清理条件，优先`transform`、`opacity`或现有能力，不把普通过渡升级为性能专项。

### 6. 修改源头并完成迁移

修改前检查数据流、父布局、共享组件和全部相关使用位置。新实现接管后删除旧组件、旧状态、旧类型、旧样式、fallback和legacy逻辑；当前范围不能全部迁移时，记录剩余位置和边界，不声称已经统一。

## Task记录

- UI Task在`Frontend Focus`中只列本次相关点，例如`DATA_SCOPE, STRUCTURE_OWNERSHIP`，不要求六点全部填`PASS`。
- 验收通过后在原Task回写实际结果、Evidence和`Spec Sync`/`Plan Sync`；实现方式变化不改PRD，产品行为变化需先确认再更新PRD或Spec。
- 评审输出只写具体问题、删除内容、正确结构、代码落点、已验证和未验证项，不使用无法指导实现的空泛形容词。
