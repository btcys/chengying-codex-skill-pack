# 项目质量门禁

把容易反复出错的工程规则变成业务项目自己的检查命令，使它们脱离工作流也能在本地和CI运行；不替代TDD、代码Review、真实页面验收或发布风险审查。

## 使用边界

仅在以下情况使用：

- 有代码的新项目准备第一个Implementation Plan；
- 长期项目首次建立质量门禁；
- 已批准Spec引入当前门禁未覆盖的新能力；
- 用户明确要求检查或建立项目门禁。

普通功能、页面、Bug或样式修改没有引入新技术能力时，只运行项目已经存在的适用命令，不重新调用本Skill。门禁按项目能力增长，不按功能数量增长。

## 1. 只读识别

先读取适用`AGENTS.md`、依赖与锁文件、已有test/lint/build命令、CI配置、目录边界，以及本次能力相关的Design-Brief、API、Schema或迁移入口。若存在`.codex/quality-gates.json`，只读取当前配置、基线和例外；不扫描无关历史文档。

识别项目是否具备UI、API、数据库与迁移、权限、媒体或重计算、多包结构和持续部署，并核对已有工具是否已经覆盖。此阶段不写文件、不安装依赖、不修改CI，只报告当前覆盖和真实缺口。

## 2. 推荐并确认

只推荐与已确认项目能力匹配、能给出确定证据的门禁。每项固定使用两行说明，技术名称可以保留，`作用`必须同时说清检查内容和能避免的实际问题：

```text
建议增加：check:migrations（数据库迁移检查）
作用：自动检查数据库改动是否有正确的升级文件并已接入发布流程，避免本地正常、上线后因数据库没更新而报错或丢数据。
```

多项推荐逐项使用相同格式，最后只提供：

```text
1. 确认增加以上门禁
2. 本版本暂不增加
```

用户可以用自然语言只选择其中几项。收到`1`或准确选择前不得生成或修改门禁；回复`2`时只在当前Plan草稿或随后建立的Plan的`Remaining`记录，本版本不重复询问。若需要新增依赖、建立新CI或明显增加运行时间，在选择前另用一句话说明。

## 3. 确认后落地

按 [门禁落地合同](references/quality-gate-contract.md) 生成最小实现：

- 配置写入业务项目的`.codex/quality-gates.json`；
- 脚本和自测写入`tools/quality-gates/`；
- 接入项目已有的包命令、Makefile或任务入口；
- 接入项目已有CI；项目没有CI时必须在推荐阶段说明；
- 每个门禁证明“违规能拦、合法代码不误报”。

优先复用项目现有工具；现有能力不足时优先采用成熟工具，但新增依赖仍需明确确认。不得把本插件中的脚本路径当作业务项目的长期运行入口，也不得写入全局目录。

## 4. 选择门禁

- 通常适用：`check:secrets`、`check:workflow-contracts`、`check:hotspots`；
- PRD已拆分为根PRD和领域PRD时：`check:product-contracts`；已配置跨层唯一来源时：`check:vocabularies`；
- 有正式UI时：`check:ui-tokens`、`check:dangling-tokens`、`check:component-contracts`；
- 确有媒体、大文件、大量数据、高频状态、批处理或同步重计算时：`check:heavy-path`；
- 按能力扩展：`check:api-contracts`、`check:boundaries`、`check:migrations`、`check:authorization-contracts`。

静态工具无法可靠判断的产品语义取舍、“是否应该复用某组件”或“两个枚举语义是否相同”只能提示；没有配置唯一来源时不得作为阻断门禁。

## 5. 运行与报告

项目统一提供`quality:fast`、`quality:pr`和`quality:release`三个逻辑入口，实际命令形式遵循项目技术栈。开发只运行相关快速门禁，合并前运行完整静态检查和测试，发布前增加构建、数据库及部署检查但不执行生产写入。

成功只报告“质量检查：全部通过”；失败报告门禁名、问题位置、影响和修复入口，不输出密钥值或无关长日志。

## 6. 旧项目基线

新项目默认零基线。旧项目只可冻结首次接入时已确认的具体历史问题，并记录位置、规则、理由、日期和关联Plan；新问题仍失败。基线只能减少，任何新增或扩大都必须重新向用户说明并确认，AI不得自动更新白名单。
