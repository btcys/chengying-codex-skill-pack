# 工作流复盘与优化

让工作流基于真实使用持续变准，同时防止因为一次失败不断增加规则、Hooks和文档。

<HARD-GATE>
只有用户明确要求复盘、优化、精简或演进工作流时才使用。普通纠正、抱怨、版本完成、新会话和开发失败都不自动触发。默认只读分析并提出建议；未经用户批准，不修改Skill、项目指令、Hooks、脚本、模板或全局配置。
</HARD-GATE>

## 输入和上下文

只读取本次复盘需要的证据：

- 用户明确反馈和本轮目标；
- 选定版本Plan中的 `FAIL-EVIDENCE` 记录；
- 已完成或被阻断的Spec、Plan、progress、Review、验证和产品验收；
- 与问题直接相关的diff、命令输出、时间或Token体量；
- 必要的当前Skill、项目指令和脚本。

不默认读取完整PRD、完整archive、全部历史对话、其他版本或旧工作流。没有足够证据时列出缺口，不从印象推导规则。

## 先分类

每个现象先归入一种根因：

1. **产品问题**：需求或验收不清，应修PRD/Spec；
2. **实现问题**：代码、测试或Review漏错，应修实现或工程检查；
3. **环境问题**：依赖、权限、端口、CI或工具不稳定，应修项目能力；
4. **流程问题**：路由、门禁、上下文、状态、职责或恢复机制重复造成成本，才进入工作流提案。

不要用流程规则掩盖前三类问题。

## 提案门槛

满足任一项才提出工作流修改：

- 同一模式在两个以上Task或版本中重复；
- 造成未授权外部操作、数据风险或真实交付阻断；
- 有证据表明它持续增加上下文、等待、Review或返工；
- 用户明确指出一条长期流程规则需要改变。

一次性偶发问题默认不改流程。没有达标模式就输出 `NO_CHANGE`。

## 复盘方法

1. 定义证据窗口，先按 [failure-evidence-contract.md](../product-spec-governance/references/failure-evidence-contract.md) 搜索选定Plan中的 `FAIL-EVIDENCE`，再按相关指针读取必要证据；
2. 列出实际路径、失败点、重复次数和可观察成本；
3. 进行产品/实现/环境/流程分类；
4. 对流程问题优先考虑删除或收窄规则，其次调整现有Skill，最后才考虑新增Skill、Hooks或状态文件；
5. 最多给三条建议，每条说明收益、风险、上下文增减、目标文件和行为测试；
6. 使用 [retrospective-template.md](references/retrospective-template.md) 输出并等待用户选择。

默认在对话中交付。只有用户要求保存时，才写入当前交付单元的 `docs/evidence/<stage>/<unit>/workflow-retrospective.md`；不建立信号队列或长期建议池。

## 批准后的边界

用户批准某条建议后，在独立实施步骤中修改准确目标；修改Skill时使用 `$zhenxin-development-workflow:writing-skills` 设计行为测试，并运行Skill、插件、上下文和相关脚本验证。不同意的建议直接结束，不保留待办提醒。

即使用户批准，也不自动安装插件、不写全局目录、不commit、不push、不创建Hooks。新Skill是最后手段，只有现有Skill和项目规则都无法承载重复模式时才考虑。
