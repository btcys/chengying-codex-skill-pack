# 接收代码Review

Review意见是待验证的技术主张，不是自动执行命令。

## 响应顺序

1. 完整读完所有意见，不立即逐条修改。
2. 用自己的话复述技术要求；不清楚就问，不猜。
3. 对照当前代码、Spec、Plan、调用方和验证证据确认意见是否成立。
4. 判断是否与批准范围、平台约束或其他意见冲突。
5. 按严重度和依赖顺序实施：阻断正确性→简单明确问题→复杂问题→非阻断改进。
6. 每组修改后运行定向验证，最后做一次定向复审。

## 来源处理

- 用户反馈：先确认理解；技术上存在风险时用代码和证据解释，不悄悄执行有害方案。
- 独立Reviewer：意见可能缺少跨Task上下文；逐条验证，不因为措辞自信就盲从。
- 多个Reviewer冲突：以批准的PRD、Spec、Global Constraints和可复核行为为准，必要时请用户裁决。

## 反对意见

当建议会破坏现有行为、超出范围、引入未使用功能、违反项目惯例或依据错误时，应给出具体技术理由和证据。不要使用空泛赞同，也不要为了显得配合先改后问。

若最初反对被证据证明错误，直接说明验证结果并修正，不需要长篇辩解。

## YAGNI检查

Reviewer提出“更完整”“更专业”的抽象、配置或扩展点时，先搜索真实调用方。当前交付没有需要时不实现；记录为建议而不是把它变成本次阻断项。

## 禁止

- 没理解全部意见就开始改；
- 跳过高严重度问题只修简单风格；
- 把Review建议当成新产品需求；
- 修复后不运行验证；
- 为了结束Review隐藏未解决问题。
