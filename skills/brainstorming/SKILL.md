# 从需求讨论到可实施设计

通过自然对话把想法变成明确设计。先理解，再选择方案，最后取得批准；不要边问边实现。

<HARD-GATE>
在向用户说明拟采用的设计并获得批准前，不写实现代码、不搭项目骨架、不调用实施Skill。设计篇幅可以缩短，批准门禁不能省略。
</HARD-GATE>

## 三种路径

先判断并告诉用户采用哪条路径，用户可以纠正：

- **Spike**：只验证可行性，输出结论，不保留为生产代码。用2～3句话说明问题和验证方法，获准后用最低成本调查。
- **Bounded**：现有仓库中边界明确的小范围改动。探索现有实现，提出简短设计、影响文件和验证方式，用户批准后直接开发，不创建Spec和Plan。
- **Architectural**：新项目、新子系统、跨模块接口或结构变化。完整进行问题澄清、方案比较、分段设计、书面Spec和用户批准，再进入Plan。

工作中发现隐藏复杂度时只能升级路径，不能为了省流程降级。

本Skill通常由总入口用于长期项目；单文件小改和确定性Bug不因本Skill单独升级为完整商业工作流。

## 过程

### 1. 理解上下文

- 先查看用户指定的产品来源、现有代码、相关测试、依赖和最近改动；涉及 UI 时同时检查根 `Design-Brief.md` 及相关设计域。
- 如果用户明确给出PRD，只把该PRD作为产品事实来源；不要自动混入其他产品或计划文档。
- 需求横跨多个独立子系统时先拆成可独立交付单元，再设计第一个单元。
- 能从代码、项目指令、批准PRD或已有测试查明的事实由代理自行调查，不转问用户。

### 2. 适度需求访谈

只在新增功能、新入口、用户流程变化、跨模块设计，或数据归属、权限、计费、持久化和验收仍有歧义时访谈。确定性Bug、样式文案微调、内部重构和已有批准Spec不重复访谈。

按路径控制强度：

- **Spike**：只确认要回答的问题、成功信号和停止条件，不展开产品访谈；
- **Bounded**：最多一轮，一次询问2～4个会改变结果的问题；
- **Architectural**：默认两轮、最多三轮；每轮3～5个当前信息已经足够回答、彼此不依赖的问题。

每个问题必须同时提供：

1. 推荐方案，放在最前并用一句话说明原因；
2. 1～2个真实可行的备选；
3. 会影响范围、体验、工程或风险的简短取舍。

用户回复“全部按推荐”即确认本轮已展示的选择，但不替代后续完整设计或Spec批准。依赖本轮答案的问题留到下一轮；必须看见才能判断的布局、密度、视觉层级和交互方案直接进入Visual Companion，不在文字访谈中反复追问。

访谈只覆盖当前交付所需的：使用者与入口、核心闭环、关键状态、数据/权限/持久化、非目标和可观察验收。以上信息明确、不再存在两种合理解释时立即停止，不为未来版本追问。

访谈中确认了稳定且项目特有的领域术语时，交由 `$zhenxin-development-workflow:product-spec-governance` 按需更新根 `CONTEXT.md`；它只统一词义，不新增产品需求。

### 3. 比较方案

- 给出2～3个可行方案及取舍，推荐项放在最前。
- 这里比较整体实现或架构方案，不重复访谈中已经确认的单点选择。
- Architectural路径涉及空项目骨架、新子系统或昂贵底层能力时，读取 [architecture-reuse-research.md](references/architecture-reuse-research.md)，先调查现有能力和成熟开源方案，再决定采用、薄适配、参考或自研。
- 删除本次交付不需要的功能和抽象。
- 现有代码有直接影响本次交付的结构问题时，允许提出局部改善；不做无关重构。

### 4. 展示设计

按复杂度分段说明：范围、架构、组件、数据流、错误处理、测试和非目标。简单部分几句话即可，复杂部分再展开。每个关键分段确认一次，不要求机械逐段确认。

设计要让每个模块职责清晰、接口明确、可独立理解与测试。

当问题本身需要“看见”才能判断时，读取 [visual-companion.md](references/visual-companion.md)。新页面、新入口、重大布局、复杂交互和关键状态设计必须先展示可视化方案；纯文字范围和技术取舍继续在对话中完成。

### 5. 形成Spec

Architectural路径将已批准设计写入：

```text
docs/specs/<stage>/<unit>-<topic>-design.md
```

写完后自查：

1. 是否存在 `TBD`、`TODO` 或占位符；
2. 各章节是否矛盾；
3. 是否足够聚焦为一份Plan；
4. 是否存在两种合理解释；
5. PRD来源、范围和非目标是否明确。

直接修正发现的问题。复杂或高影响Spec使用 [spec-reviewer.md](references/spec-reviewer.md) 做一次独立审查，然后让用户审阅书面Spec。只有用户批准后，才使用 `$zhenxin-development-workflow:writing-plans`。

## UI设计

Visual Companion负责开发前的UI方案确认，不建立独立UI线程或第二套Preview工程。涉及 UI 时先读取 `Design-Brief.md`；没有时先建立并确认最小设计规范。请求确认前必须完成组件复用、设计规范、状态与动效三项检查；用户确认的布局、交互、状态、动效和视觉约束写入Spec，开发直接实现真实产品，最后由产品验收对照确认稿和Golden检查偏差。全局设计变化才更新Design-Brief，局部变化留在当前Spec。
